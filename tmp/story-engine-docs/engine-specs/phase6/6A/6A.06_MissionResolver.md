# Phase 6A.06 — Mission Resolver

Version: 2.0
Status: LOCKED

## 1. Purpose

The Mission Resolver selects the concrete mission the protagonist must accomplish.

Resolution happens at two levels, because the source data operates at two levels:

```text
Mission Type
        ↓
Concrete Mission
```

**Mission Type** (e.g. `MISSION_RESCUE`) is an abstract ontology category (`ontology/missionTypes.json`, 21 entries, id-only). Character, Archetype, and Conflict compatibility is expressed at this level — their `best_mission_types` / `bestMissionTypeIds` fields point here, not at a specific Mission.

**Concrete Mission** (e.g. `id: 37, slug: "rescue-a-lost-friend"`) is the actual selectable story mission (`libraries/missions.json`, 100 entries). This is what the story needs — a specific mission with a name, description, and its own compatibility data (`bestLifeDomainIds`, `bestStoryActionIds`, `bestSettingIds`, `bestAdventureArchetypeIds`, `bestCoreNeedIds`).

The Mission Resolver must resolve both: first the Mission Type (from Need/Character/Archetype compatibility), then the Concrete Mission (from the Mission Type, narrowed further by direct compatibility fields on the Mission record itself).

The Mission converts the selected Need, Belief Shift, Character and Adventure Archetype into a meaningful external objective. The Mission must give the protagonist something to DO.

## 5. Resources Used

- `plannerKnowledge.missionTypeIndex` (source: `ontology/missionTypes.json`)
- `plannerKnowledge.missionIndex` (source: `libraries/missions.json`, enriched with a generated `missionTypeId` mapping — see §6 and the plannerKnowledge data contract)

The resolver must use the approved indexes rather than directly scanning `missionTypes.json` / `missions.json` when the required indexed relationships are available.

## 6. Responsibilities

**Step A — Resolve Mission Type:**

- Identify Mission Types compatible with the selected Character (`character.soft_suggested.best_mission_types`).
- Filter by Need where the Mission Type has any Need association (via Character or Archetype, since Mission Type itself carries no direct Need field).
- Filter by Adventure Archetype (`archetype.soft_suggested.best_mission_types`).
- Select one primary Mission Type.

**Step B — Resolve Concrete Mission:**

- Using `missionIndex.missionTypeId` (the generated mapping — see §12), find all concrete Missions belonging to the selected Mission Type.
- Within that candidate set, further filter/rank using the Mission's own direct compatibility fields: `bestCoreNeedIds`, `bestAdventureArchetypeIds`, `bestStoryActionIds` (used later by 6A.07, but checked here for candidate viability), `bestLifeDomainIds`.
- Ensure the Concrete Mission creates meaningful external action.
- Ensure the Concrete Mission can support the Belief Shift.
- Select one primary Concrete Mission.
- Record the reason for both the Mission Type and the Concrete Mission selection.

The Mission Resolver does not decide the individual story actions (that remains 6A.07's job — it now consumes the Concrete Mission's own `bestStoryActionIds` as a starting candidate pool, not a fresh unconstrained search).

## 7. Workflow

```text
Read Need
      ↓
Read Belief Shift
      ↓
Read Character
      ↓
Read Adventure Archetype
      ↓
Read Situation
      ↓
STEP A — Resolve Mission Type
      Get Compatible Mission Types (from Character.best_mission_types ∩ Archetype.best_mission_types)
      ↓
      Select Mission Type
      ↓
STEP B — Resolve Concrete Mission
      Look up missionIndex entries where missionTypeId == selected Mission Type
      ↓
      Filter Concrete Missions by bestCoreNeedIds / bestAdventureArchetypeIds / bestLifeDomainIds
      ↓
      Rank Remaining Concrete Missions
      ↓
      Select Concrete Mission
      ↓
Validate
      ↓
Store Mission (Concrete Mission id + reason, Mission Type trace) in Planner Context
```

## 8. Rules

MR-001 Concrete Mission must exist in the approved Mission index (`libraries/missions.json`, via `plannerKnowledge.missionIndex`).

MR-002 Mission Type must exist in the approved Mission Type index (`ontology/missionTypes.json`, via `plannerKnowledge.missionTypeIndex`).

MR-003 The selected Concrete Mission's `missionTypeId` must equal the resolved Mission Type — this link comes from the generated mapping, never from the Concrete Mission's slug or name (no slug-guessing).

MR-004 Mission Type must be compatible with the selected Character and Adventure Archetype.

MR-005 Concrete Mission must provide meaningful external action.

MR-006 Concrete Mission must support the Core Need (via its own `bestCoreNeedIds`, not merely inherited from Mission Type compatibility).

MR-007 Concrete Mission must provide an opportunity to challenge the False Belief.

MR-008 Concrete Mission must allow the True Belief to emerge through story events.

MR-009 Concrete Mission must be appropriate for the target age.

MR-010 Select exactly one Mission Type and exactly one Concrete Mission.

MR-011 Do not invent Mission Type IDs or Concrete Mission IDs.

MR-012 Mission selection must not determine Story Structure prematurely.

MR-013 The Mission Resolver must not write story prose.

## 9. Validation

Validate:

- Mission Type exists and is compatible with Character + Archetype.
- Concrete Mission exists.
- Concrete Mission's `missionTypeId` (from the generated mapping) matches the resolved Mission Type.
- Concrete Mission is active.
- Concrete Mission is age appropriate.
- Concrete Mission supports the Character (transitively, via Mission Type compatibility, and directly via its own fields).
- Concrete Mission supports the Core Need (directly, via `bestCoreNeedIds`).
- Concrete Mission supports the Adventure Archetype (directly, via `bestAdventureArchetypeIds`).
- Concrete Mission provides meaningful action.
- Concrete Mission can support the Belief Shift.
- Exactly one Mission Type and exactly one Concrete Mission are selected.

## 10. Failure Handling

If no compatible Mission Type exists:

- Return MISSION_TYPE_UNRESOLVED.
- Identify the failed compatibility relationship (Character vs. Archetype's `best_mission_types` sets did not intersect).
- Do not invent a replacement.

If a Mission Type resolves but no Concrete Mission maps to it:

- Return MISSION_UNRESOLVED, with the specific reason "no concrete mission mapped to resolved Mission Type."
- This is distinguishable from a missing/incomplete `missionId → missionTypeId` mapping (a data-layer defect, see §12) — the resolver must report which case occurred rather than treating both identically.
- Do not fall back to a different Mission Type without restarting Step A.

If multiple Concrete Missions are equally compatible within the resolved Mission Type:

- Apply the approved ranking rules.
- Use deterministic tie-breaking.
- Record the selection reason.

## 11. Deliverables

- Selected Mission Type (trace only, not a separate Blueprint field)
- Selected Concrete Mission
- Mission compatibility result
- Mission resolution trace (showing both levels)

## 12. Dependencies

Inputs

- Core Need
- Belief Shift
- Character
- Adventure Archetype
- Situation
- `plannerKnowledge.missionTypeIndex`
- `plannerKnowledge.missionIndex`, which requires the generated `missionId → missionTypeId` mapping described in the plannerKnowledge data contract. **This mapping does not exist in the raw source data** (`libraries/missions.json` has no Mission Type field) and must be produced as an audited generation step, not inferred from the Mission's slug or name text. Until that mapping exists and is populated for all 100 Missions, 6A.06 cannot run Step B for any mission lacking a mapping entry.

## 15. Example Output

```json
{
  "missionTypeTrace": {
    "id": "MISSION_DISCOVER",
    "reason": "Compatible with Character CHAR001's best_mission_types (['MISSION_DISCOVER','MISSION_SEARCH']) and Archetype ARCHETYPE_TREASURE_HUNT's best_mission_types (['MISSION_DISCOVER'])"
  },
  "mission": {
    "id": "19",
    "slug": "discover-a-hidden-treasure",
    "name": "Discover a Hidden Treasure",
    "missionTypeId": "MISSION_DISCOVER",
    "reason": "Concrete mission under the resolved Mission Type; bestAdventureArchetypeIds includes the resolved Archetype ARCHETYPE_TREASURE_HUNT directly, strengthening the match; age-appropriate, provides meaningful external action"
  }
}
```

Note: mission id 19's `bestCoreNeedIds` is `[null, null]` in the source data (unresolved) — this example illustrates that Rule MR-006 (Concrete Mission must support the Core Need via `bestCoreNeedIds`) can fail even when Mission Type and Archetype both check out cleanly. A real resolver run against this exact data would need to either fall back to a different Concrete Mission within `MISSION_DISCOVER` that does have a resolved Need match, or treat this as a data-completeness gap to flag rather than silently pass.
