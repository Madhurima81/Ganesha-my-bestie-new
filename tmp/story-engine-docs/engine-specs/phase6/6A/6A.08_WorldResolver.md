# Phase 6A.08 — World Resolver

Version: 2.0
Status: LOCKED

## 1. Purpose

The World Resolver selects the story world that best supports the Mission, Character and Adventure Archetype already resolved.

**Resolution works through a type-level bridge, because that is what the source data supports:**

```text
Resolved Archetype
      ↓
typicalWorldTypes
      ↓
match against
world.hard.world_types[]
      ↓
Candidate Worlds
      ↓
filter using Mission (via bestSettingIds → Settings.linked_world_type)
      ↓
Select World
```

**Important distinction, preserved deliberately:**

- `world.hard.world_types[]` is the **resolved, authoritative type classification** for a World — this is the primary hard-filter field.
- `archetype.typical_world_types` is a **compatibility pool** (soft-suggested, type-level) — used to generate Candidate Worlds, not to make a final selection by itself.
- `world.soft_suggested.best_adventure_archetypes_raw` is **raw text** (e.g. `"Treasure Hunt"`, `"Rescue Mission"`) — unresolved archetype *names*, not IDs. This remains soft/raw evidence only. It may be used as a tie-breaking signal (fuzzy text match against the resolved Archetype's `name`) but must never be promoted to a hard lookup field or treated as equivalent to a resolved ID relationship.

**Character and Story Actions have no data bridge to World at all.** Neither `libraries/characters.json` nor `ontology/storyActions.json` contains any field referencing a World, a World Type, or a Setting. Any instruction to "filter using Character or Story Actions" cannot be implemented as a hard filter without fabricating a field that doesn't exist in source data — so this resolver does not attempt it. If Character- or Action-aware world selection is wanted later, that requires either a new authored field on `characters.json`/`storyActions.json` (a source-library change, out of scope for this resolver) or an indirect signal through Need/Mission that doesn't currently exist either.

**Locked resolution path — the only one this resolver implements:**

```text
Archetype
   ↓ typicalWorldTypes
World.hard.world_types
   ↓
Candidate Worlds
   ↓
Mission → Setting → linked_world_type
   ↓
Final World
```

Character and Story Action pass through the Planner Context as informational fields only — carried forward for trace/logging and for downstream resolvers that may need them, but they do **not** influence World selection. This is a locked constraint, not an oversight: it exists specifically so a developer does not invent a Character↔World or StoryAction↔World compatibility check that the data cannot support. If the data model is expanded later with a genuine Character→World or Action→World field, this constraint should be revisited then — not worked around now.

Mission's bridge to World is **two hops, not one**: `mission.bestSettingIds` → `settings.json[id].soft_suggested.linked_world_type` → matched against `world.hard.world_types[]`. Settings are generic location categories (Forest, Cave, River, etc.), distinct from named Worlds (Whispering Forest, Waterfall Caves, etc.) — this separation was locked earlier in the project and is preserved here. Because Settings are generic, this filter is a **secondary/advisory narrowing signal**, not as authoritative as the direct `world.hard.world_types` match against Archetype's pool.

## 6. Responsibilities

- Build the Candidate World set: Worlds whose `hard.world_types[]` intersects Archetype's `typicalWorldTypes`.
- Resolve Mission's `bestSettingIds` to their `linked_world_type` values via `settingIndex`.
- Narrow/rank Candidate Worlds using that Mission-derived world-type pool as a secondary signal — a Candidate World whose types also appear in the Mission-derived pool ranks higher, but a Candidate World lacking that overlap is not excluded outright (the Mission→Settings→WorldType path is advisory, not authoritative, per §1).
- Optionally use `best_adventure_archetypes_raw` text matching against the resolved Archetype's name as a final tie-break only, clearly flagged as a soft/raw signal in the trace.
- Select one primary World.
- Record which signals (hard type match, Mission/Settings overlap, raw-text tie-break) contributed to the final selection.

## 7. Workflow

```text
Read Archetype.typicalWorldTypes
      ↓
Get Candidate Worlds where World.hard.world_types ∩ typicalWorldTypes ≠ ∅
      ↓
Read Mission.bestSettingIds
      ↓
Resolve each Setting ID → linked_world_type (via settingIndex)
      ↓
Rank Candidate Worlds by overlap with Mission-derived world-type pool
      ↓
[Optional] Tie-break using best_adventure_archetypes_raw text match (soft signal only)
      ↓
Select World
      ↓
Validate
      ↓
Store World in Planner Context
```

## 8. Rules

WR-001 World must exist in the approved World index.

WR-002 Primary filter is `world.hard.world_types[]` ∩ `archetype.typicalWorldTypes` — this must be non-empty for a World to be a Candidate at all.

WR-003 Mission's influence on World selection flows only through `bestSettingIds` → `settingIndex.linked_world_type`, never through a direct Mission→World field (none exists).

WR-004 Do not create or assume a `compatibleMissionIds` or `compatibleActionIds` field on the World index — neither exists in source data.

WR-005 Character and Story Actions must not be used as World filters. No source field connects them.

WR-006 `best_adventure_archetypes_raw` remains raw/soft evidence. It may inform tie-breaking only, and must be recorded as such — never treated as a resolved-ID compatibility field.

WR-007 World must be appropriate for the target age (Planner Rules general constraint — no per-World age field exists in source data).

WR-008 Select one primary World.

WR-009 Do not invent World IDs.

WR-010 World selection must not alter upstream decisions (Mission, Archetype, Character).

## 9. Validation

Validate:

- World exists and is active.
- Selected World's `hard.world_types[]` intersects Archetype's `typicalWorldTypes` (the one non-negotiable hard check).
- The Mission/Settings-derived signal was computed and recorded, whether or not it influenced the final selection.
- If a raw-text tie-break was used, it is explicitly flagged in the trace as a soft signal, not conflated with the hard filter result.
- Exactly one primary World is selected.

## 10. Failure Handling

If no World's `hard.world_types[]` intersects Archetype's `typicalWorldTypes`:

- Return WORLD_UNRESOLVED.
- Do not fall back to Mission's Settings-derived pool as a substitute hard filter — that pool is advisory only and was never intended to stand alone (§1).
- Do not randomly select a World.

If the Candidate set from Archetype is non-empty but none overlaps with the Mission-derived pool:

- Proceed with the Archetype-based Candidate set alone (WR-002 already satisfied); record in the trace that no Mission/Settings reinforcement was found — this is not itself a failure.

Note: mission id 19 (`discover-a-hidden-treasure`) is the same record flagged in `6A.06_MissionResolver.md` as having `bestCoreNeedIds: [null, null]` — that data gap is unrelated to World resolution and is not corrected here. Per the locked instruction, resolvers do not silently repair source data; a bad or incomplete upstream field surfaces as-is and belongs to data-quality/audit handling, not resolver logic.
