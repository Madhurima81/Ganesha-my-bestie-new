# Phase 6A.07 — Story Action Resolver

Version: 2.0
Status: LOCKED

## 1. Purpose

The Story Action Resolver determines the type of actions through which the protagonist will pursue the selected Mission.

**The source data has no compatibility fields on the Story Action record itself.** `ontology/storyActions.json` is a flat, id-only list of 23 actions (`ACTION_SEARCH`, `ACTION_BUILD`, `ACTION_RESCUE`, etc.) — no Mission link, no Character link, no purpose text. All compatibility is expressed from the *other* side:

- **Primary source**: the already-resolved Concrete Mission's own `bestStoryActionIds` (set by 6A.06) — this is concrete, mission-specific, and the most authoritative signal available.
- **Secondary/cross-check**: the Adventure Archetype's `typicalStoryActions` pool (set by 6A.05) — a looser, type-level signal used to validate or rank, not to hard-filter, since "typical" is advisory rather than exhaustive and the two fields are independently audited/heuristic without a guaranteed match.

The resolver translates the Mission into actionable story behavior without writing the actual story. Because the ontology carries no `purpose` text per action, the resolver must author a short contextual purpose string itself for each selected action (e.g. "Take the first step toward the Mission") — this text is resolver-authored, not sourced from any library field.

## 5. Resources Used

- `plannerKnowledge.missionIndex` (for the already-resolved Mission's `bestStoryActionIds` — this resolver does not re-derive it)
- `plannerKnowledge.adventureArchetypeIndex` (for `typicalStoryActions`, cross-check only)
- `ontology/storyActions.json` (via `plannerKnowledge.storyActionIndex`) — used only to validate that selected action IDs are real, valid ontology entries; carries no compatibility data of its own
- Planner Rules

## 6. Responsibilities

- Take the resolved Mission's `bestStoryActionIds` as the primary candidate set.
- Validate every candidate ID exists in `storyActionIndex` (catches any stale/invalid IDs in `missions.json`).
- Cross-check candidates against the Archetype's `typicalStoryActions` — actions present in both pools are preferred/ranked higher; actions present only in Mission's set are still valid (Mission is the more specific, authoritative source) but flagged in the trace as "not archetype-typical."
- Author a short `purpose` string per selected action.
- Sequence actions where the Mission implies an order (e.g. `ACTION_SEARCH` before `ACTION_DISCOVER` for a "find" mission) — sequencing is a resolver judgment call, not sourced from data, and must be recorded as such in the trace.
- Ensure actions are age appropriate (no source field for this either — apply Planner Rules' general age-appropriateness constraints, not a per-action library field).

## 7. Workflow

```text
Read Mission.bestStoryActionIds
      ↓
Validate each ID against storyActionIndex (catches invalid/stale IDs)
      ↓
Read Archetype.typicalStoryActions
      ↓
Cross-check: mark each candidate as "archetype-typical" or "mission-only"
      ↓
Author purpose text per selected action
      ↓
Determine sequence (resolver judgment, recorded as such)
      ↓
Validate
      ↓
Store Actions in Planner Context
```

## 8. Rules

SAR-001 Every selected action ID must exist in `ontology/storyActions.json` (via `storyActionIndex`) — this is an existence check only, since the ontology carries no compatibility data.

SAR-002 The primary candidate set is the resolved Mission's `bestStoryActionIds`. Do not independently search for "compatible" actions outside this set without an explicit fallback reason (see §10).

SAR-003 Archetype's `typicalStoryActions` is a soft cross-check, not a hard filter. An action present in Mission's set but absent from Archetype's typical set is still valid.

SAR-004 Do not invent Story Action IDs.

SAR-005 `purpose` text is resolver-authored per action; it must be recorded as resolver-authored (not misrepresented as sourced from a library field).

SAR-006 Any action sequencing decision must be recorded as resolver judgment, not sourced data.

SAR-007 Do not write prose (only short purpose labels).

SAR-008 Do not determine page-level execution.

SAR-009 If Mission's `bestStoryActionIds` is empty or all-null, this is a data-completeness gap in the Mission record, not a resolver failure to search harder — report distinctly from a normal unresolved case (see §10).

## 9. Validation

Validate:

- All selected action IDs exist in `storyActionIndex`.
- At least one valid action was resolved from Mission's `bestStoryActionIds`.
- Cross-check against Archetype's `typicalStoryActions` was performed and recorded (even if the result is "no overlap").
- Every selected action has a `purpose` string.
- No contradictory or duplicate actions in the sequence.

## 10. Failure Handling

If Mission's `bestStoryActionIds` is empty, all-null, or contains only invalid IDs:

- Return STORY_ACTION_UNRESOLVED with reason `MISSION_HAS_NO_VALID_ACTIONS` — distinct from a normal "no compatible action" case, since the root cause is a Mission-record data gap, not this resolver's logic.
- Do not fall back to Archetype's `typicalStoryActions` alone without flagging that the fallback occurred (Archetype's pool is type-level and less specific than a Mission-level match would have been).

If an ID in Mission's `bestStoryActionIds` does not exist in `storyActionIndex`:

- Treat as a data-integrity error in `missions.json`, report the specific invalid ID, and exclude it from the candidate set rather than silently including it.
