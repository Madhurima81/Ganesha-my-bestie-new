# Phase 6A.15 - Ending Resolver

Version: 2.0
Status: LOCKED

## 1. Purpose

The Ending Resolver determines how the story should resolve.

The real source contract is:

```text
endings.hard.ending_type
        ↓
storyTaxonomy.endingTypes[]
        ↓
Valid Ending Type
        ↓
Ending Strategy record
```

It selects a specific Ending Strategy using the real Ending Type contract, while treating Mission, Conflict, True Belief, Structure, Logic, Opening, and Beat Plan as contextual guidance only.

It does not write the ending prose.

## 2. Position in Engine

Valid Ending Type (`hard.ending_type`)
      +
Mission / Conflict / True Belief / Structure / Logic / Opening / Beat Plan (context only)
      ↓
6A.15 Ending Resolver
      ↓
Ending Plan
      ↓
6A.16 Symbol Resolver

## 6. Responsibilities

The Ending Resolver must:

- Select an Ending Strategy whose `hard.ending_type` is valid against `storyTaxonomy.json` `endingTypes`.
- Use Mission, Story Conflict, True Belief, Logic, Story Structure, Beat Plan, Opening Plan, and Character as contextual guidance for choosing among valid Ending records.
- Preserve the source-authored Ending `description`.
- Preserve the source-authored `soft_suggested.typical_emotional_resolution[]`.
- Preserve the real duplicate-type observation that `END_PASSING_FORWARD` is used by more than one Ending record, without resolving or silently deduplicating it.

## 7. Workflow

```text
Read candidate Ending records
      ↓
Validate each record's hard.ending_type against storyTaxonomy.endingTypes
      ↓
Use Mission / Conflict / True Belief / Structure / Logic / Opening / Beat Plan as contextual guidance
      ↓
Rank valid Ending records
      ↓
Select Ending
      ↓
Preserve description + typical_emotional_resolution
      ↓
Store Ending Plan
```

## 8. Rules

ER-001 Ending must exist in the approved Ending index.

ER-002 Ending's `hard.ending_type` must be a valid `storyTaxonomy.endingTypes[]` ID.

ER-003 Do not invent direct compatibility fields for Mission, Conflict, True Belief, Structure, Logic, Opening, or Beat Plan.

ER-004 Mission, Conflict, True Belief, Structure, Logic, Opening, Beat Plan, and Character may guide selection contextually, but they are not direct Ending-index compatibility fields in the real source.

ER-005 Preserve source-authored `description` and `soft_suggested.typical_emotional_resolution[]`.

ER-006 Preserve the duplicate `END_PASSING_FORWARD` observation as a visible data-quality note; do not silently deduplicate or reinterpret it.

ER-007 Do not write ending prose.

ER-008 Do not invent Ending IDs. Real IDs are `END001`-style.

## 9. Validation

Validate:

- Ending strategy exists.
- Ending ID exists in `endingIndex`.
- `hard.ending_type` is a valid taxonomy entry.
- `description` is present.
- `soft_suggested.typical_emotional_resolution[]` is preserved if present.
- Resolution trace distinguishes source-backed type validation from contextual guidance.
- Any `END_PASSING_FORWARD` selection keeps the duplicate-type observation visible in trace/metadata rather than suppressing it.

## 10. Failure Handling

If no compatible Ending exists:

- Return `ENDING_UNRESOLVED`.
- Identify whether the failure was invalid/missing `ending_type` coverage or selection deadlock among otherwise valid candidates.
- Do not invent an Ending Strategy.

If an Ending record's `hard.ending_type` is not found in `storyTaxonomy.endingTypes[]`:

- Exclude the record as an index/taxonomy integrity failure.
- Continue if other valid candidates remain.

If multiple valid Ending records share the same `hard.ending_type`:

- This is not automatically an error.
- Preserve the ambiguity as real source data, especially for `END_PASSING_FORWARD`.
- Choose among valid records contextually without claiming the duplicate was resolved at the data-contract level.
