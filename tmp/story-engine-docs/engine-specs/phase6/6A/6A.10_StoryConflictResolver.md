# Phase 6A.10 — Story Conflict Resolver

Version: 2.0
Status: LOCKED

## 1. Purpose

The Story Conflict Resolver selects the central conflict type that frames the relationship between the protagonist, Mission, and Obstacle.

**Reconciliation finding — the bridge is not what was originally assumed.** `libraries/storyConflicts.json` has no `obstacle_type` or `obstacle_function` field anywhere, and no `hard` classification field usable for matching at all — `hard.conflict_intensity` is a difficulty/tone attribute (`"High"` / `"Moderate"`), not a category link. The only fields available for resolution are two `soft_suggested` arrays, both type-level, neither authoritative in the way `hard.obstacle_domain` was for 6A.09:

```text
Obstacle.hard.obstacle_domain
        ↓
match against
StoryConflict.soft_suggested.best_obstacle_domains
        ↓
Candidate Conflicts
        ↓
reinforce (not require) using
Mission Type ∈ StoryConflict.soft_suggested.best_mission_types
        ↓
Select Conflict
```

`obstacle_type` and `obstacle_function` (both resolved by 6A.09 and available in context) are **not consumed by this resolver**, because no field on the Story Conflict record references either. They remain in the Planner Context trace for potential use by later phases, but this resolver does not filter on them — doing so would fabricate a relationship the data doesn't support.

**Real data gap, reported rather than hidden**: across the 10 Story Conflict records, `best_mission_types` covers `MISSION_RESCUE`, `MISSION_EXPLORE`, `MISSION_RETURN`, `MISSION_RECONCILE`, `MISSION_PROTECT`, `MISSION_NURTURE`, `MISSION_SOLVE`, `MISSION_DELIVER`, `MISSION_BUILD`, `MISSION_CELEBRATE`, `MISSION_MASTERY` — **`MISSION_DISCOVER` and `MISSION_SEARCH` are absent from every Conflict record.** For the running example chain (Mission Type `MISSION_DISCOVER`), Mission Type reinforcement will never fire — the resolver must handle "primary filter succeeds, secondary reinforcement structurally cannot" as a normal, honestly-logged outcome, not an error condition to paper over.

## 5. Resources Used

- `plannerKnowledge.storyConflictIndex` (source: `libraries/storyConflicts.json`)
- `plannerKnowledge.obstacleIndex` (`hard.obstacle_domain`, already resolved by 6A.09)
- `plannerKnowledge.missionTypeIndex` (the resolved Mission Type, already resolved by 6A.06)
- Planner Rules

## 6. Responsibilities

- Build the Candidate Conflict set: Conflicts whose `best_obstacle_domains` contains the resolved Obstacle's `obstacle_domain`.
- Within that set, prefer Conflicts whose `best_mission_types` also contains the resolved Mission Type — this is reinforcement, not a requirement.
- If no Candidate has Mission Type overlap (a real, expected outcome for several Mission Types per the gap above), select among the `obstacle_domain`-matched Candidates using deterministic tie-breaking, and record explicitly that Mission Type reinforcement did not occur and why (structurally absent vs. simply not matched this time).
- Carry forward `hard.conflict_intensity` for downstream resolvers/phases that may use it.

## 7. Workflow

```text
Read Obstacle.hard.obstacle_domain
      ↓
Get Candidate Conflicts where obstacle_domain ∈ StoryConflict.best_obstacle_domains
      ↓
Read resolved Mission Type
      ↓
Rank Candidates: prefer those where Mission Type ∈ best_mission_types
      ↓
If no Candidate has Mission Type overlap: record as expected/structural, proceed with obstacle_domain-only ranking
      ↓
Select Conflict (deterministic tie-break if still ambiguous)
      ↓
Validate
      ↓
Store Conflict (id, type intensity, reason) in Planner Context
```

## 8. Rules

SC-001 Story Conflict must exist in the approved Story Conflict index.

SC-002 The primary filter is `obstacle_domain` ∈ `best_obstacle_domains` — this must be non-empty for a Conflict to be a Candidate at all.

SC-003 Mission Type ∈ `best_mission_types` is reinforcement only, never a hard requirement — a Candidate lacking this overlap is still valid.

SC-004 Do not filter or rank using `obstacle_type` or `obstacle_function` — no field on the Story Conflict record supports either.

SC-005 Do not create or assume an `incorporatesObstacleIds` field (an instance-level Obstacle ID list) on the Story Conflict index — it doesn't exist; the real relationship is domain-level (`best_obstacle_domains`), not instance-level.

SC-006 When Mission Type reinforcement structurally cannot fire (the resolved Mission Type never appears in any Conflict's `best_mission_types`), this must be logged distinctly from a normal "didn't happen to match this time" case.

SC-007 Conflict must be age appropriate (Planner Rules general constraint — no per-Conflict age field exists in source data).

SC-008 Do not invent Conflict IDs.

SC-009 Select one primary central conflict.

## 9. Validation

Validate:

- Conflict exists and is active.
- Selected Conflict's `best_obstacle_domains` contains the resolved Obstacle's `obstacle_domain` (the one non-negotiable hard-equivalent check, even though the source field itself is `soft_suggested`).
- Whether Mission Type reinforcement occurred is recorded, along with which case applied (matched / didn't match / structurally impossible).
- `hard.conflict_intensity` is captured in the trace.

## 10. Failure Handling

If no Conflict's `best_obstacle_domains` contains the resolved Obstacle's `obstacle_domain`:

- Return CONFLICT_UNRESOLVED.
- Do not fall back to Mission Type alone as a substitute primary filter.
- Do not invent a conflict.
- Do not alter upstream Obstacle or Mission Type decisions to force compatibility.

If Candidates exist but none has Mission Type overlap:

- This is not a failure (see §1, §6). Proceed with obstacle_domain-only Candidates, apply deterministic tie-breaking (lowest ID) among them, and record the absence of reinforcement explicitly.

## 11. Deliverables

- Candidate Conflict set (trace)
- Compatibility result (obstacle_domain match confirmed; Mission Type reinforcement status)
- Conflict resolution trace
