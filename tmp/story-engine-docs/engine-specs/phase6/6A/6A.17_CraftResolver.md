# Phase 6A.17 - Craft Resolver

Version: 2.0
Status: LOCKED

## 1. Purpose

The Craft Resolver carries forward Beat-required craft dependencies and records whether their semantic validation is currently possible.

The real source contract is:

```text
Beat.required_craft[]
        ↓
CR codes
        ↓
Craft Resolver
        ↓
Known / unresolved dependency
```

This resolver is currently **blocked by missing source coverage** for craft-technique definitions. The uploaded library bundle contains real `required_craft[]` codes inside `beats.json`, but does **not** contain a verified craft-definition library or combination matrix that explains what those codes mean.

It therefore does not invent technique definitions, does not infer the meaning of any `CR-*` code, and does not create a fake craft index from the codes themselves.

It does not write prose.

**Current source-coverage reality:** there is no verified uploaded craft-definition library backing `craftTechniqueIndex`. At this stage, the resolver can only carry forward CR codes observed in Beats and mark semantic validation as blocked.

## 6. Responsibilities

The Craft Resolver must:

- Collect all real `required_craft[]` codes referenced by the resolved Beat Plan.
- Distinguish between:
  - no craft required
  - craft required but definition unavailable
- Carry CR codes forward exactly as sourced.
- Mark semantic validation as blocked where no verified definition source exists.
- Preserve the missing-source condition as a data-layer blocker rather than hiding it inside resolver heuristics.

## 7. Workflow

```text
Read Beat Plan
      ↓
Collect required_craft[] codes
      ↓
Any codes present?
      ↓
No -> record no craft required
      ↓
Yes -> carry codes forward exactly
      ↓
Check for verified craft-definition source coverage
      ↓
No verified source -> mark semantic validation blocked
      ↓
Store Craft dependency plan
```

## 8. Rules

CF-001 Do not invent `storytellingTechniques.json` or `techniqueCombinationMatrix.json`.

CF-002 Do not infer what a `CR-*` code means.

CF-003 Do not create a fake Craft index from the CR codes themselves.

CF-004 Carry real `required_craft[]` codes forward exactly as sourced from Beats.

CF-005 Mark semantic validation as blocked by missing source coverage whenever craft definitions are unavailable.

CF-006 Distinguish explicitly:
  - no craft required
  - craft required but definition unavailable

CF-007 Do not claim age-appropriateness, emotional suitability, or compatibility validation for a craft code whose definition source is missing.

CF-008 Do not write prose.

CF-009 Do not determine final page text.

## 9. Validation

Validate:

- Every carried craft dependency came from a real Beat `required_craft[]` field.
- No CR code was renamed or expanded.
- The resolver clearly distinguishes `no_craft_required` from `definition_unavailable`.
- Missing source coverage is preserved as a blocker in trace/output rather than hidden.

## 10. Failure Handling

If the Beat Plan contains no `required_craft[]` codes:

- Return a successful empty/no-op Craft dependency result.
- Record `no_craft_required`.

If the Beat Plan contains one or more `required_craft[]` codes but no verified craft-definition source exists:

- Do not invent technique definitions.
- Return the CR codes as unresolved dependencies.
- Record `CRAFT_DEFINITION_SOURCE_MISSING`.

If a later source bundle provides verified craft-definition coverage:

- Re-run this resolver against that source rather than retrofitting meaning into old runs.
