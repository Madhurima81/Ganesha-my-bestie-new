# Phase 6A.01 — Planner Entry

Version: 1.0
Status: LOCKED

## 1. Purpose

Planner Entry initializes the Planner Context from the incoming Story Request.

It establishes the validated starting information that all downstream resolvers may use.

It does not make story-selection decisions beyond normalizing and validating the request.

## 2. Position in Engine

Story Request
      ↓
6A.01 Planner Entry
      ↓
6A.02 Need Resolver

## 3. Inputs

- Story Request

The request may contain:

- Target age
- Life domain
- Situation
- Core need
- Language
- Product constraints
- Page range
- Other explicitly supported story requirements

## 4. Outputs

- Initialized Planner Context
- Normalized Story Request
- Request constraints
- Planner execution metadata

## 5. Resources Used

- Planner Rules
- plannerKnowledge
- Request validation rules

6A.01 must not directly resolve downstream story components.

## 6. Responsibilities

- Validate the incoming request.
- Normalize supported request fields.
- Preserve explicit user constraints.
- Initialize Planner Context.
- Record request provenance.
- Identify required planning inputs.
- Establish the starting state for 6A.02.

## 7. Workflow

```text
Read Story Request
      ↓
Validate Request
      ↓
Normalize Supported Fields
      ↓
Preserve Constraints
      ↓
Initialize Planner Context
      ↓
Record Provenance
      ↓
Pass to Need Resolver
```

## 8. Rules

PE-001 Do not invent missing story decisions.

PE-002 Do not resolve Need, Belief, Character or Mission.

PE-003 Preserve explicit user constraints.

PE-004 Unsupported request fields must not be silently converted into decisions.

PE-005 Request normalization must not change user intent.

PE-006 Planner Context must identify the source Story Request.

## 9. Validation

Validate:

- Story Request exists.
- Required request fields are present.
- Target age is valid where supplied.
- Page constraints are valid where supplied.
- Referenced IDs exist where the request explicitly provides IDs.
- No contradictory constraints exist.

## 10. Failure Handling

If the request is invalid:

- Stop planner execution.
- Identify the invalid field.
- Record the failure.
- Do not invent a replacement.

## 11. Deliverables

- Planner Context
- Normalized Story Request
- Request validation result

## 12. Dependencies

Inputs

- Story Request
- Planner Rules

Next Module

- 6A.02 Need Resolver

## 13. Runtime Notes

- Stateful: No
- Expected execution order: First planner component
- Idempotent: Yes
- Cacheable: Yes
