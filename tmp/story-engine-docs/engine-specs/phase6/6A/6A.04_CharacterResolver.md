# Phase 6A.04 — Character Resolver

Version: 2.0
Status: LOCKED

## 1. Purpose

The Character Resolver selects the protagonist who is best suited to experience and express the selected Need.

Character selection is based on emotional suitability, not simply appearance or popularity.

The resolver first determines the appropriate Character Role and then selects the best specific character.

**Note on Belief Shift**: `libraries/characters.json` has no belief-related field of any kind — confirmed absent, same pattern as the Mission/Archetype and Mission/Logic gaps found elsewhere in this reconciliation. Character compatibility is expressed only via `best_need_ids`, `best_ganesha_symbols`, `best_mission_types`, and `best_logic_families` (all confirmed present, see plannerKnowledge data contract). Rule CR-002 below ("Character must be compatible with the Belief Shift") predates this reconciliation and currently has no supporting data field — it is left in place as a placeholder pending a decision from the project owner, and must not be silently enforced by inventing a Belief compatibility check the data doesn't support.

## 6. Responsibilities

The resolver must answer:

> Which child is most likely to grow through this emotional journey?

It must:

- Determine the appropriate Character Role (`hard.roleId`).
- Identify candidates whose `best_need_ids` includes the resolved Core Need.
- Filter to the resolved Character Role.
- Rank remaining candidates (in practice, several Roles in the current 18-character library have exactly one representative — see `6A.10`-style honesty note in §10: a single-candidate outcome is normal, not a resolution failure).
- Select one protagonist.
- Preserve character diversity when multiple candidates are similarly suitable (only relevant when a Role has more than one member).

## 7. Workflow

```text
Read Need
      ↓
Get Candidate Characters where Need ∈ best_need_ids
      ↓
Determine Character Role from Candidates (or from Need-compatible Roles generally)
      ↓
Filter to Role
      ↓
Rank remaining candidates (if more than one)
      ↓
Select Protagonist
      ↓
Validate
      ↓
Store Character in Planner Context
```

## 8. Rules

CR-001 Character must naturally support the selected Need (`Need ∈ character.best_need_ids`).

CR-002 [Placeholder — no supporting data field exists] Character must be compatible with the Belief Shift. Retained pending a decision; must not be enforced by inventing a field.

CR-003 Character Role is resolved before specific character selection.

CR-004 Character must be age appropriate (Planner Rules general constraint — no per-Character age field exists in source data).

CR-005 Character must be active.

CR-006 Character must exist in the approved character index.

CR-007 If multiple candidates score similarly, apply controlled character variety.

CR-008 Character must have a plausible growth path (derived from `trait_id`, not a separate library field — see §1).

CR-009 Character remains fixed after resolution unless explicitly regenerated.

CR-010 One protagonist is selected for the story.

CR-011 Ganesha is never selected as the protagonist. Satisfied structurally: `libraries/characters.json` contains 18 animal protagonists and no Ganesha record at all — there is nothing to exclude, this is not a generator-side filter.

CR-012 Character Resolver does not decide Mission, World, Logic or Ending — it only supplies the compatibility pools (`best_mission_types`, `best_logic_families`) those later resolvers read.

## 9. Validation

Validate:

- Character Role exists.
- At least one candidate exists whose `best_need_ids` includes the resolved Core Need.
- Selected character exists and is active.
- Protagonist is unique.

## 10. Failure Handling

If no character's `best_need_ids` includes the resolved Core Need:

- Return CHARACTER_UNRESOLVED.
- Do not select a random character.
- Do not weaken the Need to force a match.

If exactly one candidate exists for the resolved Role (a normal, common outcome in the current 18-character library — several Roles have only one member):

- This is not a failure. Select that candidate directly; record in the trace that no ranking among alternatives was needed.

## 15. Example Output

```json
{
  "character": {
    "role": "ROLE_UNDERDOG",
    "candidates": ["CHAR010"],
    "selected": "CHAR010",
    "reason": "CHAR010 (Anu, Mouse) is the sole ROLE_UNDERDOG character in the current 18-character library; best_need_ids ['NEED_COURAGE','NEED_IDENTITY','NEED_CONFIDENCE'] includes the resolved Core Need NEED_CONFIDENCE."
  }
}
```

Verified directly against `libraries/characters.json`: `CHAR010` is Anu (Mouse), `hard.role_id: "ROLE_UNDERDOG"`, `hard.trait_id: "TRAIT_DETERMINED"`, `best_need_ids: ["NEED_COURAGE","NEED_IDENTITY","NEED_CONFIDENCE"]`. No other character in the library shares `ROLE_UNDERDOG` — this is a single-candidate resolution, not a multi-candidate ranking, and the spec now says so explicitly (§10) rather than implying a false choice between two options.
