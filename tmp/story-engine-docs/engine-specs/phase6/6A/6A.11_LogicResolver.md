# Phase 6A.11 — Logic Resolver

Version: 2.0
Status: LOCKED

## 1. Purpose

The Logic Resolver determines the narrative logic family governing how the story's events causally connect.

**Three legitimate compatibility bridges feed into Logic, all confirmed against real source data:**

```text
Character.best_logic_families
        +
Archetype.best_logic_families
        +
Conflict.best_logic_families
        ↓
Logic Family intersection / ranking
```

`ontology/logicFamilies.json` is **id-only** (14 entries, no other fields at all — no `causalPattern`, no description). This resolver does not read causal-pattern data from the library, because none exists. Any causal pattern or sequence text associated with the selected Logic Family (e.g. for later use by 6A.13 Beat Resolver or Phase 7) is **resolver-authored**, derived from the Logic Family's name/id and the surrounding story context — never presented as if it came from the source library.

**Mission contributes nothing directly to Logic.** `libraries/missions.json` has no logic-related field of any kind — confirmed absent. Do not fabricate a Mission→Logic path.

**Character's `best_logic_families` is real, authored data with 100% coverage** (confirmed present on all 18 character records, one value each) — this was verified before being added as a compatibility pool, not assumed.

## 6. Responsibilities

- Read all three pools: Character's `best_logic_families`, Archetype's `best_logic_families`, Conflict's `best_logic_families`.
- Compute the 3-way intersection first.
- If the 3-way intersection is non-empty, select from it (deterministic tie-break if more than one value).
- If empty, rank by pairwise overlap count (a Logic Family appearing in 2 of 3 pools outranks one appearing in only 1), with Character's pool taking tie-break priority when overlap counts are equal — Character is the most specific-to-protagonist source among the three, per the locked priority order.
- If no overlap exists across any pair, fall back to Character's pool alone (Character is listed first in the locked priority and is present with 100% coverage, making it the most reliable single source).
- Validate the selected Logic Family ID exists in `logicIndex`.
- Author a short causal-pattern description for the selected Logic Family, clearly flagged as resolver-authored.
- **Explicitly distinguish two different failure/degraded modes** (see §10): "pools exist but don't overlap" vs. "a pool itself was empty or missing" — these have different root causes and must not be logged identically.

## 7. Workflow


## 8. Rules

LR-001 Logic Family must exist in the approved Logic index (`ontology/logicFamilies.json`, id-only).

LR-002 The three compatibility pools are Character, Archetype, and Conflict `best_logic_families` — in that priority order for tie-breaking.

LR-003 Mission must not be treated as a Logic filter — no such field exists.

LR-004 Do not read `causalPattern` or any sequence data from `logicFamilies.json` — it doesn't exist there. Any causal pattern text is resolver-authored and must be labeled as such in the output.

LR-005 A 3-way intersection is preferred over a 2-way, which is preferred over a single-pool fallback. Always record which tier was used.

LR-006 Distinguish explicitly: (a) pools were populated but did not intersect ("no overlap" — a normal, expected outcome for some combinations), vs. (b) one or more pools were empty/missing entirely ("missing compatibility data" — a data-completeness gap, logged differently). Given Character's confirmed 100% coverage, case (b) should only arise from Archetype or Conflict, not Character.

LR-007 Do not invent Logic Family IDs.

LR-008 Select exactly one Logic Family.

LR-009 Logic Family selection must not alter upstream Character, Archetype, Conflict, or Mission decisions.

## 9. Validation

Validate:

- Selected Logic Family exists in `logicIndex`.
- The intersection tier used (3-way / 2-way / single-pool fallback) is recorded.
- If single-pool fallback was used, the reason is recorded (no pairwise overlap found) and which pool was used.
- Resolver-authored causal-pattern text is present and explicitly flagged as authored.

## 10. Failure Handling

If all three pools are populated but share no common value at any tier, and Character's pool alone is used as final fallback:

- This is not a failure — proceed with Character's single value, clearly logged as a single-pool fallback (per §6, §8 LR-005/LR-006).

If Character's pool is unexpectedly empty (contradicting its confirmed 100% coverage — would indicate a data regression):

- Return LOGIC_UNRESOLVED with reason `CHARACTER_LOGIC_DATA_MISSING` — flagged as a data-integrity anomaly requiring investigation, since this pool was verified to always be populated in the current library.

If Archetype's or Conflict's pool is empty (a known, more plausible gap given their smaller record counts):

- Proceed with whatever pools remain populated; record which pool(s) were missing as `missing compatibility data`, distinct from a populated-but-non-overlapping case (LR-006).
