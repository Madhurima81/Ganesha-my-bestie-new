# Phase 6A.02 - Need Resolver

Version: 2.0
Status: LOCKED

## 1. Purpose

The Need Resolver determines the Core Need that the story should address.

The selected Need becomes the primary internal growth target for the story.

The real source-backed Need path is:

```text
Explicit Need
   or
Situation.hard.need_id
   ↓
Core Need
```

`ontology/coreNeeds.json` is a Need ontology file, not a rich compatibility library. It provides the canonical Need IDs and definitions, but does **not** provide per-Need age bands or direct life-domain compatibility tables. When a Situation is available, the real hard bridge is `situation.hard.need_id`.

## 2. Position in Engine

Planner Context
      ↓
6A.02 Need Resolver
      ↓
6A.03 Belief Resolver

## 3. Inputs

From Planner Context:

- Life domain
- Situation, if supplied
- Explicit Core Need, if supplied
- Other validated request constraints
- Target age - general Planner Rules context only, not a source-backed Need field

## 4. Outputs

- Resolved Core Need
- Need resolution trace
- Need compatibility result

## 5. Resources Used

- `plannerKnowledge.needIndex`
- `plannerKnowledge.situationIndex`
- Planner Rules

The resolver must use the approved planner indexes rather than directly scanning source libraries.

## 6. Responsibilities

- Determine the appropriate Core Need.
- Respect an explicitly supplied Need.
- Resolve a Need from the selected Situation where appropriate.
- Validate that the Need ID exists in the approved Need index.
- Treat target age and life domain as general request/planner context, not as direct Need-library compatibility fields unless such a source-backed field exists.
- Record why the Need was selected.

## 7. Workflow

```text
Read Planner Context
      ↓
Check Explicit Need
      ↓
If absent, resolve from Situation.hard.need_id
      ↓
Validate Need ID in needIndex
      ↓
Record request/planner-context checks
      ↓
Store Need in Planner Context
      ↓
Pass to Belief Resolver
```

## 8. Rules

NR-001 An explicit valid Need takes precedence over inferred selection.

NR-002 Never invent a Need ID.

NR-003 Need must exist in the approved Need index.

NR-004 When a Situation is available, Need must align with the real `situation.hard.need_id` field.

NR-005 Do not invent a direct Need<->Life Domain compatibility table if the source data does not provide one.

NR-006 Do not enforce per-Need age compatibility from invented fields such as `ageRange`; no such source-backed Need field exists in `ontology/coreNeeds.json`.

NR-007 Do not select multiple competing Core Needs unless the planner contract explicitly permits them.

NR-008 The Core Need is the primary growth target.

## 9. Validation

Validate:

- Need exists.
- Need is traceable either to an explicit request value or to `situation.hard.need_id`.
- Situation exists when Situation-driven resolution is used.
- Selection is traceable.
- Any age/life-domain handling is clearly marked as general planner/request-context checking rather than direct Need-library compatibility.

## 10. Failure Handling

If no valid Need can be resolved:

- Stop dependent resolution.
- Return `NEED_UNRESOLVED`.
- Identify the source of the conflict.
- Do not fabricate a Need.

If an explicit Need conflicts with a selected Situation's `hard.need_id`:

- Return a validation conflict.
- Do not silently replace either value.

## 11. Deliverables

- Resolved Core Need
- Need resolution trace
- Compatibility result
