# Phase 6A.18 - Planner Validator

Version: 2.0
Status: LOCKED

## 1. Purpose

The Planner Validator is the final validation gate for Phase 6A.

It validates the complete set of resolved planning decisions against the **reconciled Phase 6A architecture only**.

It does not repair or silently modify planner decisions.

It must distinguish:

- **blocking integrity failures** - the planner output violates a real required contract or contains broken references
- **known upstream data-coverage blockers** - the planner output is structurally honest, but an earlier resolver was forced to stop at a declared source-data gap

Neither category is a successful validation result, but they are not the same kind of failure and must not be reported identically.

## 6. Responsibilities

Validate the complete planner chain for:

- Completeness of required resolver outputs
- ID/reference integrity
- Real hard-bridge integrity only
- Correct `hard` vs `soft_suggested` usage
- Causal/progression integrity where the real source supports it
- Context-only fields not being misrepresented as compatibility contracts
- Known upstream data-coverage blockers being surfaced explicitly
- Protagonist agency

The Planner Validator must **not** reintroduce compatibility assumptions that were removed during reconciliation.

## 8. Rules

PV-001 Every required planner decision must exist unless a resolver explicitly returned an allowed blocked/unresolved state documented by the reconciled contract.

PV-002 Every referenced ID must resolve against the approved knowledge/index layer for that resolver's real source contract.

PV-003 Need must align with Situation through the real Situation/Need bridge.

PV-004 Belief Shift must align with the selected Situation/Need contract actually used by the reconciled Belief flow.

PV-005 Character must validate against the real Character contract (`CHAR<NNN>`, `hard.roleId`, `hard.traitId`, real `best*` fields only).

PV-006 Adventure Archetype must validate through the real Mission Type bridge from Character `best_mission_types`, not through invented Need/Character direct fields.

PV-007 Mission must validate through the real two-level Mission contract, and any unresolved `missionId -> missionTypeId` dependency must be surfaced explicitly as a **data-coverage blocker**, not silently ignored.

PV-008 Story Actions must validate through real Story Action IDs and the reconciled Mission/Archetype bridges only.

PV-009 World must validate through the real Archetype world-type bridge plus the Mission `bestSettingIds -> setting -> linked_world_type` bridge only.

PV-010 Obstacle must validate through the real Archetype obstacle-domain bridge only.

PV-011 Story Conflict must validate through the real Obstacle Domain / Mission Type contract only, including any known Mission Type coverage gaps being preserved honestly.

PV-012 Logic must validate through the real Character / Archetype / Conflict logic-family pools only.

PV-013 Story Structure must validate only through `hard.logic_family -> selected Logic`. Do not check invented Structure/Mission/Conflict/Age compatibility fields.

PV-014 Beat Plan must validate through the real Beat graph: `allowed_logic[]`, `next_beats[]`, `state_change`, `repeatable`, and `max_repeats`. Do not validate an invented direct Structure->Beat mapping.

PV-015 Opening must validate only through `hard.opening_type -> storyTaxonomy.openingTypes[]`. Do not validate an invented Beat->Opening compatibility contract.

PV-016 Ending must validate only through `hard.ending_type -> storyTaxonomy.endingTypes[]`, preserving the known `END_PASSING_FORWARD` duplicate-type observation. Do not validate invented direct Ending->Mission/Conflict/Belief compatibility fields.

PV-017 Symbols must validate only through the Ganesha Symbol contract: `ganeshaSymbols.id -> symbol_theme -> symbolThemes[]`, plus real `best_need_ids` / `best_mission_types` usage. Do not validate invented generic symbol/world/beat compatibility contracts.

PV-018 Craft must validate only CR-code presence/propagation from Beat `required_craft[]`. Do not validate semantic meaning where no craft-definition source exists.

PV-019 Missing craft-definition coverage must be surfaced explicitly as a **data-coverage blocker** when CR codes are required but unresolved, and must be distinguished from the non-blocking case where no craft is required.

PV-020 Context-only fields (Belief, World, Beat Plan, Structure, Opening, Ending, etc. depending on resolver) must not be treated as if they were direct compatibility contracts when the reconciled source data does not support that interpretation.

PV-021 Protagonist must retain meaningful agency.

PV-022 No blocking integrity failure may remain.

## 9. Validation

Each validation result must contain:

- Rule ID
- `PASS` / `FAIL` / `BLOCKED` / `WARNING`
- Severity
- Affected component
- Evidence
- Responsible resolver
- Regeneration target or required upstream data work where applicable

A blocking integrity failure prevents Story Blueprint creation.

A known upstream data-coverage blocker also prevents Story Blueprint creation, but must be labeled `BLOCKED`, not `FAIL`, when the planner output is otherwise honest and contract-compliant.

Warnings do not block Blueprint creation unless explicitly configured as blocking by Planner Rules.

## 10. Failure Handling

The Planner Validator must not silently modify Planner Context.

For every blocking integrity failure:

1. Identify the failed rule.
2. Identify the affected component.
3. Identify the responsible resolver.
4. Produce a regeneration target.
5. Return the issue upstream.
6. Re-run affected resolution.
7. Run Planner Validation again.

For every known upstream data-coverage blocker:

1. Identify the blocked contract.
2. Identify the missing source coverage.
3. Identify the affected resolver.
4. Report the blocker as data-layer work, not as a silent planner defect.
5. Prevent Blueprint-ready status until the blocker is resolved or explicitly accepted by project policy.

If the issue is caused by a library/index defect rather than planner logic, report the library defect instead of changing the planner decision.
